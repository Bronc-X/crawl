# WeChat Auto-Reply MVP 实施计划

Status: Proposed v1
Date: 2026-04-22
Source PRD: `docs/prd-wechat-auto-reply.md`

## 1. 一句话目标、边界与成功标准

目标：
在 Mac 或 Windows 机器上，围绕已登录的桌面微信，实现可持续运行的一对一会话自动回复助手：能检测新消息、做二分类路由、自动发送低风险标准回复，并在必须转人工时自动通知固定人工微信号，同时保留完整审计记录。

边界：
- 只做桌面客户端可见界面的 UI 级自动化
- 第一版支持 Mac 与 Windows 两个平台
- 只支持单机、单账号、单操作员
- 第一版只支持一对一私聊，不做群聊、不做批量外联
- 运行形态优先为 CLI/守护进程，可从 `cmd`、`PowerShell`、`bash` 启动；不强制要求桌面控制台
- 不做协议逆向、内存注入、凭证提取、隐藏后台发信
- 不混入 listing/crawl 相关业务

成功标准：
- 可连续运行一个工作日，不需要人工盯守
- 低风险 FAQ / 素材请求在目标 SLA 内自动回复
- 必须转人工的话题不自动回复客户，而是自动通知固定人工微信号
- 每次识别、路由、发送、失败、转人工都有可追溯日志和截图

## 2. 当前项目现状

已存在：
- `docs/prd-wechat-auto-reply.md`
- `docs/prd-multi-platform-stable-listing.md`

尚不存在：
- 代码仓库骨架
- 运行时依赖定义
- 测试工程
- 本地数据目录
- 打包与部署脚本

结论：
这是一个从 0 到 1 的新项目，最重要的不是“把所有能力一次性堆进去”，而是先拿下三个硬验证点：
1. 能稳定发现新消息
2. 能稳定读到可用上下文
3. 能稳定完成一次可验证发送

## 3. MVP 范围裁剪

第一版强约束：
- 单机单账号单操作员
- 同时覆盖 Mac 与 Windows
- 仅支持一对一私聊
- 默认以“自治优先”运行，只有命中红线时才转人工
- 自动发送只开放给白名单 FAQ / 素材请求
- 转人工时自动给固定人工微信号发送通知
- 本地优先：日志、截图、素材索引、知识库都先落本地
- 远程报表、团队协作、审批流、账号切换一律后置

第一版建议支持的自动回复场景：
- 已审核 FAQ 文本回复
- 已审核素材发送：文本 + 单文件附件
- 简单问候/收到确认/资料索取

第一版必须转人工的场景：
- 价格、折扣、退款、合同、法律、投诉
- 明显情绪化沟通
- 连续发送失败
- UI 异常、焦点异常、无法确认发送结果

明确延期：
- 多账号切换
- 群聊
- 复杂素材包编排
- 云端协同后台
- 自动跟进提醒
- 质量评分与绩效报表

## 4. CEO Review

### 4.1 业务价值

这个产品的真正价值不是“自动回消息”，而是把运营同学最重复、最容易不一致、又最消耗注意力的那部分工作做成稳定系统：
- 把首响速度从“看人”变成“看规则”
- 把回答质量从“靠记忆”变成“靠知识库”
- 把运营产能从“增加人头”变成“增加标准化处理量”

### 4.2 用户核心路径

核心路径应保持为 6 步闭环：
1. 系统检测到微信新消息
2. 提取最近上下文和联系人信息
3. 风险分级：低风险 / 必须转人工
4. 执行动作：自动发送 / 通知固定人工微信号并冻结该会话自动处理
5. 验证发送结果并写审计日志
6. 系统继续运行，人工只处理被升级的话题

如果任何一步不能给出高置信结果，就转人工，而不是“猜着发”。

### 4.3 关键边缘场景

| 场景 | 风险 | 第一版处理 |
|---|---|---|
| 微信弹窗、更新提示、文件选择框遮挡 | 误识别/误点击 | 进入 `guarded pause`，截图并提醒 |
| 操作员正在输入 | 与自动化抢焦点 | 自动化让出优先级，不执行发送 |
| 消息抽取不完整 | 回答跑偏 | 直接转人工 |
| 同一联系人连续失败 | 重复骚扰 | 标记 `manual-only` |
| 同一句 FAQ 高频到达 | 处理压力大 | 允许模板自动回复 |
| 非白名单问题命中 LLM | 风险不可控 | 不直接对外发送，只用于内部增强或直接转人工 |

### 4.4 产品参考矩阵

| 方案类型 | 优点 | 缺点 | 本项目取舍 |
|---|---|---|---|
| 协议机器人 | 自动化能力强 | 合规和封控风险高 | 明确不选 |
| 纯坐标脚本 | 上手快 | 极脆弱，UI 一变就坏 | 不作为主方案 |
| 通用企业 RPA 平台 | 能力全 | 部署重、学习成本高、定制成本高 | 只作为后备方案 |
| 自治优先桌面代理 | 自动化程度高、仍可审计、贴合真实流程 | 首版要认真做状态机与升级机制 | 选这个 |

### 4.5 产品决策

- 产品定位锁定为“自治优先的桌面微信代理”，不是被动等待人工逐条审核的工具。
- 默认心智是“机器处理绝大多数标准场景，人工只接升级单”。
- 系统的第一职责是稳定自动完成低风险流程，并在不确定时正确升级。
- 人工需要能一眼看懂当前状态、最近动作、失败原因和被升级的客户线索。

## 5. Eng Review

### 5.1 技术路线结论

建议第一版采用“共享核心 + 平台执行器”方案：
- 共享核心：Python 3.10，负责状态机、规则、日志、素材映射、知识检索、人工升级策略
- 运行形态：CLI/守护进程优先，可由 `cmd`、`PowerShell`、`bash` 启动
- 存储：SQLite + 本地文件目录
- OCR：PaddleOCR，仅在平台自动化接口拿不到稳定信号时启用
- 平台执行器：
  - Windows：优先评估 Astron RPA 作为执行器，`pywinauto` 作为对照基线
  - macOS：基于 Apple 的 Accessibility / UI Scripting 能力实现独立执行器

这条路线的原因是：
- 你已经把首版约束改成了 Mac + Windows，所以任何 Windows-only 方案都不能直接成为总架构
- 既然界面可以先不做，那么最简单稳定的控制平面就是 CLI/守护进程
- 真正需要共享的是状态机、规则、知识、日志；真正平台相关的是“怎么读微信”和“怎么点微信”
- 这样我们既能认真评估 Astron 对 Windows 风险的帮助，又不会把 Mac 路径堵死

### 5.2 Astron 需要重新评估，但不能直接成为全栈前提

经查官方资料后，结论如下：
- Astron RPA 的官方仓库把桌面自动化、图像识别、调度、API/MCP 接入打包在一起，对 Windows 自动化友好
- 但其官方系统要求里客户端运行环境明确偏向 Windows 10/11，不能直接覆盖 macOS 首版目标
- `pywinauto` 官方文档明确是 Windows GUI Automation Library，只能用于 Windows，对双平台首版不够
- Apple 官方文档提供了基于 Accessibility 的 UI Scripting 路径，这说明 macOS 侧必须单独做执行器

因此更合适的结论不是“上 Astron”或“不上 Astron”，而是：
- 总架构不绑定 Astron
- Windows 执行器把 Astron 列为主候选，需要先做可行性 spike
- macOS 执行器必须独立实现
- 控制层、规则层、日志层、知识层保持与执行器解耦

### 5.6 复杂度评估

高风险复杂点：
- Windows 与 macOS 两端的微信 UI 结构不一致，需要双执行器
- 自动发送后如何验证“真的发出去了”，不能只靠按回车
- 转人工时要切换到固定人工联系人并完成通知，再恢复原状态
- 微信桌面端暴露信息可能不稳定，可能需要自动化接口和截图/OCR 双通路

次高复杂点：
- 同一联系人会话状态维护
- OCR 结果噪声导致的错误路由
- 素材发送结果确认
- 守护进程和微信前台窗口之间的同步时序

中低复杂点：
- FAQ 规则管理
- 本地检索与引用展示
- CLI 运行态的可观测性输出

### 5.7 分阶段验证门

Phase 1: 双平台可行性门
- Windows 侧能发现新消息、读出最新文本、发送固定文本
- macOS 侧能发现新消息、读出最新文本、发送固定文本
- 能给固定人工微信号发送升级通知
- 能记录截图与错误

Phase 2: 运营闭环门
- 能对 FAQ / 素材请求做规则路由
- 能对异常状态降级
- 转人工后会话被冻结，不继续自动处理

Phase 3: 知识增强门
- 能做知识检索
- 能用知识增强自动回复或升级通知内容
- 不影响主状态机稳定性

Phase 4: 稳定性门
- 可运行整日
- 失败可回放
- 重试、熔断、manual-only 逻辑稳定

## 6. 建议开发顺序

### Step 1. 先做双平台执行器可行性 spike

先只交付四件事：
1. Windows 执行器验证：
   - Astron 路径
   - `pywinauto` 对照路径
2. macOS 执行器验证：
   - Accessibility / UI Scripting 路径
3. 两端都完成：
   - 检测一对一会话的新消息
   - 自动发送固定文本
   - 给固定人工微信号发送升级通知
4. 记录本地日志和失败截图

不先碰：
- LLM
- 知识库
- 复杂 UI
- 远程服务

原因：
如果双平台执行器这一步跑不通，后面所有“智能能力”都没有落点。

### Step 2. 再做规则化自动回复

加入：
- FAQ 白名单
- 红线拦截
- 素材映射
- manual-only
- 固定人工通知模板

### Step 3. 再接知识库增强

加入：
- 本地知识切片
- 检索召回
- 引用展示
- 回复增强模板

### Step 4. 最后做稳定性硬化

加入：
- 异常 UI 状态识别
- 更稳的发送验证
- 失败熔断
- 可回放日志
- 打包与安装

## 7. 非目标与不做事项

本轮不做：
- 任何逆向协议能力
- 任何规避微信安全控制的能力
- 任何无人工边界的大规模触达能力
- 任何与 listing/crawl 业务混合的能力
- 任何“先做架构平台，后补业务验证”的空转建设

## 8. 当前建议与待确认点

我建议按下面这组前提启动开发：
- 前提 1：第一版支持 Mac 与 Windows，但架构采用共享核心 + 平台执行器
- 前提 2：第一版只做单机、单账号、一对一私聊
- 前提 3：默认以“自治优先”运行，只有命中红线时才转人工
- 前提 4：转人工时，自动给固定人工微信号发送通知
- 前提 5：控制平面先跑在 CLI/守护进程中，不强制要求桌面 GUI
- 前提 6：Windows 执行器先做 Astron vs `pywinauto` 可行性对比，再决定最终落地
- 前提 7：素材自动发送第一版只覆盖文本和单文件附件

还需要明确 1 个最终拍板点：
- Mac 与 Windows 是否要求在第一版同时达到可用，而不是“Windows 先上线、Mac 紧随其后”

如果这些前提通过，我就按这个实施计划开始搭项目骨架，并优先完成双平台 Phase 1 可行性 spike。
